# ADR 0011: Gateway API ingress, replacing the retired ingress-nginx

- **Status:** Accepted, 2026-10-30; all three phases done (removal: phase C, below)
- **Decided by:** Amit Kumar (AKS application routing Gateway API, over Envoy Gateway,
  Application Gateway for Containers and Traefik)
- **Departs from:** the LLD's NGINX ingress controller (Compute, Edge). The LLD's
  intent — one ingress behind Front Door, locked to our profile, canary releases with
  analysis — is kept; the controller changes.
- **Implements:** stack 05 (`azapi_update_resource.gateway_api`), stack 06 (the gateway's
  IP and a second Front Door origin), `infra/gitops/base/edge`,
  `infra/gitops/base/api/httproute.yaml`, the Argo Rollouts plugin
  (`applications/dev/argo-rollouts.yaml`), and `tools/ci/tests/test_gitops.py`.

## Context

- ingress-nginx is retired upstream: maintenance ended in March 2026, so there are no
  more releases or security fixes
  ([Kubernetes, 2025-11-11](https://kubernetes.io/blog/2025/11/11/ingress-nginx-retirement/);
  [Steering and SRC statement, 2026-01-29](https://kubernetes.io/blog/2026/01/29/ingress-nginx-statement/)).
- Microsoft supports its managed NGINX (the application routing add-on) only until
  November 2026, and names the add-on's Gateway API implementation as the successor
  ([AKS docs](https://learn.microsoft.com/en-us/azure/aks/app-routing-gateway-api);
  [migration guide](https://learn.microsoft.com/en-us/azure/aks/app-routing-nginx-to-gateway-api-migration)).
  Ours is the open-source chart, installed by `scripts/bootstrap-cluster.sh`, so it had no
  vendor patching at all.
- On 2026-10-30 our controller image (v1.15.1, the last release) scanned at 50 critical
  and 201 high findings (Go stdlib, OpenSSL, curl, nginx 1.27.1). It is the
  internet-facing hop behind Front Door.

AKS chooses the Istio version for the cluster's Kubernetes version and upgrades it in
place. On our cluster it deployed v1.30.5, not the v1.31.3 compared above: 2 critical
and 17 high in each image (Go stdlib, `x/net`, Azure Linux's OpenSSL, `go-jose`), all
fixed in later builds. Still far below nginx's 50 / 201, and Microsoft's to roll out,
not ours to patch.

## Decisions

1. **The AKS application routing add-on's Gateway API implementation**
   (GatewayClass `approuting-istio`).
   - Microsoft builds, patches and upgrades it in place with the cluster.
   - It is the AKS default on new Automatic clusters from 1.36.
   - Enabled with stack 05 through `azapi` (managed Gateway API CRDs plus
     `appRoutingIstio`), as Microsoft's own Terraform sample does; azurerm has no field.
2. **Both Front Door locks are kept.**
   - Lock 1: only the `AzureFrontDoor.Backend` service tag reaches the IP (the stack 01
     NSG, and the `azure-allowed-service-tags` annotation on the Gateway's Service).
   - Lock 2: every API route matches our profile's `X-Azure-FDID` exactly (the
     HTTPRoute, value from the dev overlay). A request without it matches no rule and
     gets **404**, where nginx returned 403. `/healthz` stays open for Front Door's probe.
3. **The gateway lives in its own namespace, `platform-edge`**: default-deny, baseline
   Pod Security (its proxy pods are generated by the add-on, not by us). The route
   stays with the API in `platform-api`; the Gateway accepts routes from that namespace
   only.
4. **Canary releases move to the Argo Rollouts Gateway API plugin** (v0.17.0).
   - Installed from its image mirrored into ACR by digest, copied by an init container,
     and pinned by the binary's SHA-256. The controller never downloads it at runtime.
   - The binary in the image differs from the GitHub release asset of the same version
     (likely a separate build); we pin what we ship.
   - The binary itself has 18 critical/high findings (Go stdlib, `x/net`, `grpc`), all
     fixed upstream. It runs inside the Rollouts controller and talks only to the
     Kubernetes API. **Open:** rebuild it from the v0.17.0 source with current Go.
5. **Images come from Microsoft's registry, not ours.** Like KEDA and the CSI driver,
   the gateway is an AKS add-on: AKS chooses and patches its images, and mirroring
   them would only freeze them. This is a recorded exception to "images only from the
   platform registry".
6. **Three phases, so traffic never moves until the new path is proven.**
   - **A — side by side.** The gateway gets its own static IP and a Front Door origin that
     is **disabled**. Gateway, route, policies, the Rollouts plugin and Prometheus
     scraping deploy; nginx still carries everything. Proven from inside the cluster:
     the route answers with the header, 404s without it, and the proxies' metrics
     reach Prometheus.
   - **B — cutover, one commit and one apply.** Enable the gateway origin at priority 1
     and move nginx's to priority 2: Front Door sends everything to the gateway and
     fails over to nginx by itself if the gateway's health probe fails. There is never
     a moment with no enabled origin. Switch the Rollout to the plugin, and the
     analysis to the gateway's metrics (`istio_requests_total` and
     `istio_request_duration_milliseconds_bucket`, `reporter="source"`, confirmed in
     A; latency is in milliseconds, so the threshold is 500). Argo CD ignores the
     route's weights and the plugin's in-progress label.
   - **C — removal.** ingress-nginx (uninstalled), its IP and Front Door origin
     (stack 06), the API's Ingress, the network-policy and Prometheus rules for it,
     its values files, and the bootstrap script's install. A test fails if any comes
     back. There is no failover origin any more: rolling back means reinstalling it.
   - Rollback before C: swap the two origins' priorities back, and the Rollout to
     `trafficRouting.nginx`. Until then the nginx Ingress serves the stable API.

Phase B's first canary (api `8277a3d`, 2026-10-30) was aborted by its own analysis:
the canary's Istio series exists only after its first request, and a 2-minute rate
needs two samples, so the queries returned nothing for the first minutes. Argo
Rollouts counts empty as an error, not a pass. Each query now falls back to NaN
("no traffic yet"). The old version served throughout.

Phase C caused a partial dev outage, 2026-10-30 from about 12:25 UTC. The gateway's
Service used the add-on's default, `externalTrafficPolicy: Cluster`, so the load
balancer sent Front Door to all five nodes. Only the app subnet's NSG admits Front
Door; the system subnet's dropped the connections, and Front Door answered 504 for
roughly 40% of new connections. nginx had used `Local` and so never touched system
nodes, and Front Door's long-lived connections hid the difference until uninstalling
nginx made the cloud provider rewrite the load balancer. The gateway now uses `Local`
(the add-on's documented Service customisation), and a test keeps it there.

## Consequences

- **Lost from nginx, not needed today:** the add-on has no gateway-level rate limiting,
  header or body size limits, or Lua (no `EnvoyFilter`). Front Door's WAF already
  inspects request bodies, and can rate-limit if needed.
- **Upgrades are Microsoft's, in place.** Minor Istio upgrades follow AKS upgrades and
  new releases. The add-on keeps at least two proxy replicas with a disruption budget,
  but an upgrade can still disrupt traffic. Our maintenance window applies to the
  cluster, not to every add-on rollout.
- **Private mode (UAT, production):** the same Gateway takes
  `azure-load-balancer-internal` annotations. Front Door Private Link to an internal
  load balancer is still to be wired (stack 06).
- The Front Door to origin hop stays plain HTTP in public mode, as before.
